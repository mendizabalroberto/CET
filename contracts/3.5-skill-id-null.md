## 1 · El problema

`learning_events.skill_id` viene NULL en el 100 % de las filas de produccion, y
por eso el indice `learning_events_skill_ts_idx` —que es parcial,
`where skill_id is not null`— no indexa nada y no sirve para ninguna consulta.
El codigo de la skill si viaja: llega dentro de `payload.skillCode`, en la
columna JSONB, donde ningun indice lo alcanza.

## 2 · La evidencia que ya tenemos

`apps/web/src/app/api/events/route.ts`, linea 143, construye cada fila asi:

```
    skill_id: event.skillId ?? null,
```

`packages/shared/src/events.ts`, linea 76, declara ese campo como opcional:

```
  skillId: z.string().uuid().optional(),
```

y **ningun emisor lo rellena nunca**. Lo que si se rellena es el codigo, en
`apps/web/src/components/learn/practice-machine.ts`, linea 172:

```
    skillCode: question.item.skillCode,
```

que acaba en `payload`. Es decir: `event.skillId` es siempre `undefined`, el
`?? null` se cumple siempre, y la columna queda NULL siempre.

La migracion `supabase/migrations/0010_telemetry.sql` lo confirma por el otro
lado — la columna existe y el indice la exige no nula:

```
 43:  skill_id        uuid,
 98: create index learning_events_skill_ts_idx
 99:   on public.learning_events (skill_id, server_ts desc)
100:   where skill_id is not null;
```

## 2 bis · Como se llama de verdad la columna

La columna de codigo de `public.skills` se llama **`code`**, a secas. **NO** se
llama `skill_code`. `supabase/migrations/0005_curriculum.sql`, lineas 188-199,
literal:

```
  code            text not null,   -- 'math.fractions.simplify'
  name            jsonb not null,  -- I18nText
  ...
  constraint skills_code_uniq unique (course_id, code),
  constraint skills_code_format
    check (code ~ ...minusculas, puntos y guiones bajos...),
```

Dos cosas se siguen de ahi, y las dos importan:

- La consulta es `.select("id, code").in("code", codigos)`.
- Un `skillCode` real tiene la forma `math.fractions.simplify`: minusculas,
  puntos y guiones bajos. Un codigo como `MATH-ADD-001` **no pasa** el check de
  la base. Usa codigos con la forma real en los tests.

## 3 · El criterio de aceptacion

`pnpm --filter @cet/web exec vitest run src/app/api/events` sale en verde, con
tests nuevos que demuestran, sobre el `route.ts` real:

1. Un evento que llega **sin** `skillId` pero **con** `payload.skillCode` acaba
   insertando una fila con `skill_id` **no nulo**, igual al `id` de la skill
   cuyo codigo es ese.
2. Un evento que llega **con** `skillId` explicito conserva ese valor: la
   resolucion por codigo no lo pisa.
3. Un `payload.skillCode` que no corresponde a ninguna skill deja `skill_id` en
   NULL y **no** hace fallar el lote entero. Perder el indice de una fila es
   malo; perder el evento del alumno es peor.
4. La resolucion se hace en **una sola consulta para todo el lote**, no una por
   evento. El comentario de la linea 131 ya explica por que el lote se inserta
   de una vez; la misma razon vale aqui.

Escribe los tests en el fichero de test existente de esa ruta, siguiendo su
estilo de dobles. La consulta de resolucion debe ir por el cliente que ya usa
el modulo, no por uno nuevo.

## 4 · Que NO cuenta como resuelto

- **Inventarse el nombre de una columna.** Un intento anterior consulto
  `skill_code` y sus tests pasaron en verde, porque el doble de Supabase del
  fichero de test le daba la razon: contra la base real la consulta habria
  fallado entera. El doble no es la base. Toda columna que nombres tiene que
  existir en `0005_curriculum.sql`, y esta se llama `code`.
- Rellenar `skill_id` con el propio `skillCode` textual: la columna es `uuid` y
  la clave ajena a `public.skills (id)`. Un dato plausible no es un dato
  correcto.
- Un test que afirme sobre el objeto que tu mismo construyes en el test en vez
  de sobre las filas que `route.ts` pasa a `.insert(...)`. Una asercion que
  compara un valor consigo mismo ya paso aqui siete veces en un dia.
- Cambiar `packages/shared/src/events.ts` para hacer `skillId` obligatorio:
  esta fuera del territorio, y romperia a todos los emisores.
- Un `if` de resolucion envuelto en una condicion que nunca se cumple con los
  datos de los tests. Comprueba que tu test **falla** si borras la resolucion,
  y dilo en el comentario del test.
- Tocar el indice o la migracion: el indice esta bien; lo que estaba mal era el
  dato.
- Dejar dos comentarios de seccion numerados igual. Si insertas un apartado
  antes del «--- 4. Insert masivo», renumera.
